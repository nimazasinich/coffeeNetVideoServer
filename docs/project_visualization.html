🔄 Queue Engine Architecture

  • Singleton Pattern: queue_engine object
  • Job States: pending → queued → dispatching → active → completed/failed
  • Concurrency Control: Semaphore + drive locking
  • Priority Queue: Jobs sorted by priority + timestamp
  • Atomic Dispatch: Status update in single transaction
  • Recovery: Stale job detection on startup

🔌 WebSocket Architecture

  • Customer Hub: /ws/jobs for UI updates
  • Agent Hub: /ws/agent/{id} for remote control
  • Events: job.created, job.progress, job.completed, drive.connected
  • Reconnection: Auto-reconnect with exponential backoff
  • Ping/Pong: 20-second heartbeat

Data Flow Diagrams

📀 USB Copy Flow (Local)

1. Customer Selection
Customer browses media → selects items → adds to cart → chooses USB drive
↓
2. Job Creation
POST /api/jobs → creates job (status: pending) → validates media exists → checks drive space
↓
3. Payment Confirmation
Admin confirms cash payment → POST /api/admin/payment/confirm → job status: queued
↓
4. Queue Dispatch
Queue engine picks job → atomic status update (queued → dispatching → active) → acquires drive lock
↓
5. File Copy
Copy engine streams file in 512KB chunks → writes to .tmp file → reports progress via WebSocket
↓
6. Verification
Compute SHA-256 checksum → compare with stored checksum → verify integrity
↓
7. Completion
Rename .tmp → final file → release drive lock → job status: completed → broadcast to UI

🖥️ USB Copy Flow (Agent)

1-3. Same as Local
Customer selection → job creation → payment confirmation
↓
4. Agent Dispatch
Queue engine identifies agent drive (format: agent_id:drive_letter) → sends WebSocket command
↓
5. Agent Download
Agent receives command → downloads from /api/media/{id}/stream → streams to local USB
↓
6. Progress Reporting
Agent sends progress updates via WebSocket → server updates DB → broadcasts to UI
↓
7. Agent Completion
Agent computes checksum → sends completion message → server marks job completed

📱 Mobile Download Flow

1. Customer Selection
Customer selects media → chooses mobile delivery → provides phone number (optional)
↓
2. Job Creation
POST /api/jobs (delivery_type: mobile) → creates job (status: pending)
↓
3. Payment & Token Issuance
Admin confirms payment → generates HMAC-SHA256 signed token → stores nonce in DB → job status: active
↓
4. Customer Download
Customer opens download URL → GET /api/download/{job_id}?token=xxx → verifies token signature
↓
5. Token Validation
Check expiry → verify nonce not used → check daily IP quota → mark token as used (atomic)
↓
6. Throttled Streaming
Stream file with bandwidth throttle → support HTTP Range requests → compute SHA-256 on-the-fly
↓
7. Completion
Stream finishes → mark job completed → record download audit → update statistics

🔐 Authentication Flow

  1. Admin enters username/password
  2. POST /api/admin/login
  3. Server verifies bcrypt hash
  4. Issues JWT token (15-min expiry)
  5. Client stores token in localStorage
  6. All admin requests include Authorization header
  7. Server validates JWT on each request

💳 Stripe Payment Flow

  1. Customer chooses online payment
  2. POST /api/payment/create-session
  3. Server creates Stripe Checkout session
  4. Customer redirected to Stripe
  5. Customer completes payment
  6. Stripe sends webhook to /api/payment/webhook
  7. Server verifies signature → enqueues job
  8. Issues download token (mobile) or starts copy (USB)

💾 Database: SQLite with WAL Mode

✅ Advantages

  • Zero configuration
  • Single file deployment
  • ACID transactions
  • WAL mode: concurrent reads
  • No separate DB server
  • Embedded in application

⚠️ Limitations

  • Single writer at a time
  • No horizontal scaling
  • Limited to ~100 writes/sec
  • No built-in replication
  • File-based locking
  • Max 50-80 cafés realistically

WAL Mode Configuration:

PRAGMA journal_mode=WAL
PRAGMA foreign_keys=ON
PRAGMA synchronous=NORMAL

⚠️ Critical Vulnerabilities

CRITICAL Path Traversal (CVE-Risk)

Location: backend/main.py:282, backend/mobile_delivery.py:219

Issue: Media paths loaded from DB without validation. If attacker can inject malicious path, arbitrary file read possible.

Attack Vector:

media["path"] = "/etc/passwd"
GET /api/media/{id}/stream → reads /etc/passwd

Mitigation: Function safe_path_under_root() exists but is NEVER CALLED

Fix Required: Add path validation before all file operations

CRITICAL Agent Impersonation

Issue: No cryptographic authentication for agents. Any client can register as agent.

Attack Vector:

POST /api/agent/register → get ws_token
Connect to /ws/agent/{id} → receive job assignments

Impact: Attacker can steal media files, inject malware into USB drives

Fix Required: Certificate-based mutual TLS or pre-shared keys

HIGH No HTTPS Enforcement

Issue: System runs on HTTP by default. No redirect to HTTPS.

Impact: Credentials, tokens, customer data sent in plaintext

Fix Required: Add HTTPS redirect middleware, HSTS header

HIGH Hardcoded Secret Key

Default: CHANGE_THIS_IN_PRODUCTION_SUPER_SECRET_KEY_32CHARS

Issue: No enforcement to change default secret

Impact: JWT forgery, download token forgery if default used

Fix Required: Fail startup if default secret detected

📊 Scalability Analysis: 100 Internet Cafés

ScaleConcurrent JobsDB Writes/secWebSocket ConnectionsStatus

Bottleneck Analysis:

  • SQLite WAL Limit: ~100-200 writes/sec practical (1000 theoretical)
  • At 100 cafés: 133 writes/sec sustained → hitting limits
  • Symptoms: "database is locked" errors, job failures, UI freezes
  • Solution: Migrate to PostgreSQL or implement write queue

💾 Database Write Operations per Job

  1. INSERT job (1 write)
  2. UPDATE job status 4× (pending → queued → active → completed)
  3. INSERT payment (1 write)
  4. INSERT sale (1 write)
  5. UPDATE drive lock 2× (lock → unlock)
  6. Progress updates: 10-50× per job (file size dependent)

Total: 20-60 writes per job

At 100 cafés: 400 jobs × 20 writes = 8,000 writes over ~60 seconds = 133 writes/sec
